# Gemma 4 26B-A4B experiments

The 26B-A4B shares the Gemma 4 engine with the 31B; its attention, sampling
and MTP decisions are in the [31B experiments](../gemma-4-31b/EXPERIMENTS.md).
The rows below cover the expert layers. Decode rates are `gufo bench` tg128
on UD-Q4_K_XL unless stated; the draft A/Bs are HTTP (`tools/gemma4/draft_policy_bench.py`).

| Experiment | Decision / evidence |
| --- | --- |
| Prefill activation format | Retained binary16. Rounding every projection input to Q8_1, the 31B's and llama.cpp's prefill format, costs mean KL 0.74 against FP32 on a chat prompt (attention output alone 0.44); BF16 0.066; binary16 3.7e-5 ([Quality](QUALITY.md#activation-precision)). Q8_0 projections run Flash-Next's binary16 WMMA GEMM, experts its routed binary16 GEMM |
| Decode expert kernel | Retained: a Gemma routed GEMV over FP32 activations that groups each forward's slots by expert, decodes the weights once and applies them to up to four slots; a slot's FMA order depends only on its row, so verification equals decode. llama.cpp-style Q8_1 vector kernels (Flash-Next's `qfn` MMVQ) rejected unmeasured on the precision result above |
| Routed GEMV shape | Retained after a split-K sweep with cold experts (a fresh eight of 128 per launch): Q4_K gate/up 8 experts 95 µs with eight waves per row group, 86 µs with four, 91 µs with one; the 704-wide down projection is fastest with whole rows per wave (Q5_1 55 µs, 218 GB/s). Decoding 64-value Q4_K tasks (one header load per sub-block pair) instead of 32: neutral, kept |
| Experts beside the dense MLP | Retained: at decode and verification widths the routing, expert GEMVs and GeGLU run on a second stream while the dense MLP runs, joining before the mixture. tg128 51.8 → 52.4 |
| Fused residual norms | Retained: the post-attention norm also writes the expert input (same RMS scale); mixture, post-FFN norm and the next layer's input norm are one 1024-thread kernel; decode-width residual norms use 1024-thread blocks (256-thread blocks were latency bound, 15 µs per call). tg128 49.0 → 51.0 → 53.2. The norm's reduction order moves decode KL between 1.3e-6 and 2.7e-5 through routing near-ties ([Quality](QUALITY.md#routing-sensitivity)) |
| Fused Q/K/V and gate/up projections | Retained: parts sharing a format are uploaded back to back and projected in one launch at decode widths and in binary16 prefill. tg128 53.2 → 53.3; the 31B's AR decode (same change set) 11.39 → 11.61 |
| Q6_K prefill experts (UD-Q6_K_XL) | Retained: a Gemma routed binary16 WMMA GEMM for Q6_K gate/up (Flash-Next's routed GEMM stages one scale per 32 values; Q6_K scales every 16). pp2048 387 (16-row FP32 fallback) → 2488 |
| Prefill router | Retained: `ffn_gate_inp.scale` folded into the router at load (the product the decode kernel formed per launch, so decode is unchanged); prefill logits as one hipBLAS SGEMM per layer, the RMS scale applied per row in top-k. Router 1.5 → 0.6 ms per 2048-row layer |
| Prefill mixture width | Retained: 1024-thread blocks for every width. 256-thread blocks spilled their 24-value rows: 43 ms per 2048-row layer instead of 1.4 |
| Binary16 expert outputs in prefill | Rejected: pp2048 3329 → 3433 but prefill KL 3.7e-5 → 2.7e-4 on the short prompt (the conversation check unchanged) |
| MTP draft costs | Retained: the calibrated policy prices cycles with the 26B's own table (verification 18.3 ms for one row to 30.7 ms for eight at d0, drafter step 1.8 ms). Against the dense 31B's table, HTTP d0, ABA: prose 72.1 → 77.0 tok/s, sampled story 59.2 → 64.7, code 113.2 → 115.4 ([artifact](artifacts/draft-costs-ab-d0k.json)) |
| Draft policy | Retained calibrated. HTTP d0 against confidence: prose +3.7%, code +2.3%, sampled story -1.3%, repetitive -3.6%; fixed two or three drafts lose 12–44% on code and repetitive text ([artifact](artifacts/draft-policy-ab-d0k.json)). Greedy text identical under every policy |
| MTP for single-user decode | Retained: despite the extra experts every verified row reads, calibrated MTP decodes mixed prose at 78.1 tok/s against 50.7 tok/s AR over HTTP at d0 (48.8 vs 36.7 at 131K) |
| Batch-aware calibrated drafting | Retained ([31B row](../gemma-4-31b/EXPERIMENTS.md)). Each extra verified row pulls in more experts, so per-session drafting left batched MTP behind batched AR (C8 187 vs 210 tok/s). Pricing drafts against the whole forward and letting a session verify none, UD-Q4_K_XL mixed: C2 107 → 113, C4 148 → 155, C6 173 → 192, C8 187 → 208 tok/s; repetitive C6 179 → 219, C8 192 → 208, C2 225 → 216 |
| Q8_0 verification past eight rows | Retained: the shared exact 9–16-row Q8_0 kernel (bit-identical to decode, `gemma4.projection_ops`) at every shape through `hip::LaunchQ8_0SmallBatchWide`; the Qwen dispatch reads unlisted shapes in eight-row passes. Verification at d0: 9 rows 37.2 → 31.9 ms, 16 rows 48.4 → 43.5 ms; vocabulary head at 9 rows 6.8 → 3.4 ms. With the re-measured costs batched MTP mixed moved −1% and repetitive +3% (single samples) |
| Smaller split-attention chunks | Rejected. The 26B's 8 sliding and 2 global KV heads give decode attention few workgroups (a full window: 24 blocks, 47 µs per sliding layer). Chunks of 64 keys (hd256) and 256 (hd512) instead of 128 and 512, tg: d2048 51.1 → 51.7, d32768 46.5 → 47.0, d131072 36.9 → 36.4 (merge cost), MTP d32768 162.9 → 164.1; the 31B unchanged. 32/128 lost 1–2% at 32K |
| MTP costs measured on repetitive vs varied text | Retained varied prose. The first table came from a 16-word repeated vocabulary, whose rows share experts; on English prose extra rows cost up to 15% more (8 rows 30.7 → 31.8 ms at d0, 34.6 → 39.6 at 16K). Single user unchanged (prose 77.0 / 76.7, code 116.4 / 117.9); multi-user mixed summed over C1–C8 +1.3% (UD-Q4_K_XL) and +2.6% (UD-Q6_K_XL, C8 195 → 202). UD-Q6_K_XL mixed at C4 still trails batched AR (132 vs 143): each session's drafter chain runs on its own, eight serial drafter steps per C4 cycle |
| Batched drafter chains | Retained. The sessions of a batch draft together: one drafter forward per step over every chain still running (shared projections and head, attention per session) and one host wait, each session's policy deciding its own row against the batch as it stands and a share of the drafter step. A lone session runs the same kernels as before (d2048 bench 144.3 either way). Multi-user MTP HTTP, UD-Q4_K_XL mixed C2/C4/C6/C8 117/149/188/210 → 134/180/207/219 tok/s, repetitive 241/221/204/227 → 263/248/222/253; UD-Q6_K_XL mixed 94/132/175/202 → 110/150/189/193 (C8 below batched AR, 205), repetitive 217/227/198/216 → 246/257/219/249 |
| Sliding split attention: chunks per workgroup | Retained two instead of four. The hd256 waves of a split block share nothing, so the packing only sets the grid (a full window: 24 → 40 workgroups); every split's arithmetic is unchanged. tg d2048 50.6 → 51.0, d32768 46.1 → 46.35, MTP d2048 143.9 → 144.4; the 31B tg d2048 11.03 → 11.06. One chunk per block: 50.9 / 46.3 |
| QkvPost heads per workgroup | Rejected: one wave per head either way; one, two or four heads per block instead of eight (a decode row: 24 or 18 blocks instead of 3) left tg d2048 at 50.9–51.0 |
| Routed down projection tile rows | Retained 64 instead of 48, from a second tile map. Per 2048-row layer: Q5_1 3049 → 2966 µs, Q8_0 (UD-Q6_K_XL) 3041 → 2965 µs, about 0.4% of a chunk (pp2048 within noise). Gate/up stays at 48: the shared Q4_K/Q5_K kernel has no wider tile |
| Dense binary16 GEMM tiles for Gemma shapes | Retained per shape; the generic 256×128 tile (one K block per stage, 4×2 waves) stays for Q/K/V and gate/up. Per 2048-row call, current / two-block stage 8×1 / one-block 8×1 / 128-row tiles: QKV 2380 / 2482 / 2476 / ≥2959 µs; attention output 2013 / **1759** / 2126 / ≥1831; gate/up 1201 / 1281 / 1214 / ≥1436; down 605 / 697 / **582** / ≥746. pp2048 3350 → 3381 |
| 4096-row prefill chunks | Rejected: the same 4096-token prompt as one chunk instead of two, pp4096 3267 → 3308 (+1.3%), for about 400 MiB more sliding-window ring, twice the expert scratch and twice the chunk time that decoding sessions wait behind. 48-row expert tiles fill equally at both widths (128 and 256 assignments per expert on average) |
| Q6_K prefill gate/up: weight staging | Retained. Each lane had loaded its own row's 64 code bytes per 32-value K block (both half-waves the same bytes, `ql` twice and `qh` four times per super-block, 16 cache lines per load): removing the weight loads alone took the kernel from 8.6 to 3.7 ms. Now two threads per row fetch half a super-block (96 code bytes, scales, d) one stage ahead into LDS (112-byte rows, conflict-free), four K blocks per barrier pair, and dead 16-row parts of a tile are skipped, which makes 96-row tiles free of padding work. Per 2048-row layer 11.05 → 4.32 ms (48-row tiles 6.3, 128 rows 4.7); outputs unchanged (target KLs identical to the previous kernel). UD-Q6_K_XL pp2048 2567 → 3437. Prefetching the old per-lane loads one block ahead: 11.05 → 10.94; 16-byte-aligning them: no gain |
| Q4_K / Q5_K prefill gate/up in the Gemma routed GEMM | Retained: the staged Q6_K kernel generalised to Q4_K and Q5_K (80- and 112-byte staged rows, the same binary16 FMA per weight as Flash-Next, so outputs are bit-identical to its routed GEMM, `gemma4.moe_ops`), over 96-row tiles. Q4_K gate/up per 2048-row layer 4.58 → 3.79 ms; UD-Q4_K_XL pp2048 3381 → 3554. Q8_0 gate/up (layer 29 of UD-Q6_K_XL) stays on Flash-Next's kernel |
| Device-built expert tile maps | Retained: the per-layer copy of the expert counts to the host, its wait and the map upload are replaced by a one-block kernel that scans the counts into both maps and pads them with tiles past every bucket, which the routed GEMMs skip; the GEMMs launch the map capacity. Prefill no longer waits on the host inside a forward. pp2048 3554 → 3592, outputs unchanged |
| Producers write the binary16 prefill inputs | Retained: attention, the post-attention norm (dense and expert inputs), the dense GeGLU and the mixture write each projection input's binary16 copy next to the FP32 row, replacing five narrowing passes per layer. pp2048 3592 → 3622, outputs unchanged. The copies round the stored FP32 value: left to itself the compiler folded the attention epilogue's product into a mixed FMA rounding once to binary16 (about 3 in 10^5 values an ulp off, long-conversation KL 0.027 → 0.033), so the value is pinned in an FP32 register first |
| Skip FP32 rows no prefill kernel reads | Retained: when every consumer of a binary16 prefill input is a Q8_0 projection (all of them on both quants), its producer writes only the binary16 copy: attention output, the norm's dense and expert inputs, the dense GeGLU and the mixture's next-layer input, about 120 MB of writes per 2048-row layer. The last layer keeps its FP32 rows for the head and the drafter. pp2048 3622 → 3786, outputs unchanged |
| Q5_1 prefill down projection in the Gemma routed GEMM | Retained: 64-value stages (three 16-byte pieces per row, neighbouring threads on neighbouring pieces), 96-row tiles with dead parts skipped, and each token tile's FP32 results transposed through LDS so a token's 128 outputs leave as one 512-byte store; the same binary16 FMA per weight as Flash-Next (bit-identical, `gemma4.moe_ops`). Per 2048-row layer 2950 → 2534 µs; UD-Q4_K_XL pp2048 3786 → 3851. The Q8_0 down of UD-Q6_K_XL stays on Flash-Next's kernel |
| Prefill router without hipBLAS | Rejected: a router kernel with the decode router's arithmetic (bit-identical logits) and 32 token rows per block staged in LDS for 16 expert waves took 785 µs per 2048-row layer against the SGEMM's 625 (pp2048 3851 → 3822), and moved prefill quality both ways (conversation KL UD-Q4_K_XL 0.0274 → 0.0288, UD-Q6_K_XL 0.021 → 0.028). hipBLAS takes about 550 µs standalone in either operand orientation |
